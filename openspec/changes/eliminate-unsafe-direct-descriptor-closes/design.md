## Context

See `proposal.md` for motivation. The repository now has a lightweight `docker.filesystem` foundation with `CleanupFailures`, `OwnedDescriptor`, `DirectoryDescriptor`, and injectable descriptor operations. A final ownership inventory still identifies explicit and implicit descriptor ownership in npm regular-file work, runtime artifact verification, build-context writing, artifact/build-cache traversal, materialization, rendering, persistent cache writing, snapshots, and project state.

The preliminary Phase 7 inventory found fd-owning subprocess streams in `execution.py::_close_stream_pipes`, `SubprocessExecutor.run_streaming` and its cleanup hooks, and `lifecycle.py::{close_descriptors,reap_process,terminate_and_reap,run_captured}`. Original Phase 6B replaced repeated raw closes with stream owners. Subsequent review exposed rejection that closes caller-owned streams, fallible lock construction after launch, adoption-failure precedence gaps, and joins that can skip cleanup or release a pipe beneath a live reader. Historical test results in `phase6b-verification.md` remain evidence for that implementation, not acceptance of the revised architecture. The replacement is four ordered subphases under 6B, centered on reusable process ownership.

A direct descriptor-close call remains appropriate only inside raw POSIX adapters, inside `OwnedDescriptor.close()`, `OwnedStream.close()`, or an equivalent shared-owner implementation after it has made ownership terminal, and as the principal operation of a handoff whose releasing parent is already terminal and whose child is already tracked by the surrounding ownership-aware failure path. Every consumer-owned integer descriptor—including a success-path release outside `finally` and a lifecycle object's release method—uses `OwnedDescriptor`; an already fd-owning file object uses `OwnedStream` instead of giving its `fileno()` to a second owner. The defects include masking `finally` closes, implicit file-object ownership from `os.fdopen(..., closefd=True)`, unadopted raw descriptors from `tempfile.mkstemp()`, unowned single releases, nonterminal/multi-resource close loops, and handoffs whose ledger cannot account for an opened child after parent close failure.

Completed 6BA and baseline 6BB.1–6BB.13 now provide prevalidated streams and a generic local-process owner, including subsequent active-primary, first-interruption and publication-race corrections. That acceptance remains valid for its original scope, but the current immediate reader cancellation and hardcoded local terminate/kill sequence do not provide the planned configurable stop-policy API. The generic extension must pass 6BB.14–6BB.25 before behavior-preserving consumer migration. Docker operation wrapper states and cooperative container-control behavior are outside this change's scope.

The foundation remains below `docker.transactions` and every domain package. Npm and versioning leaves may import explicit `docker.filesystem` submodules, but `docker.filesystem` must not import them or acquire their path, cache, recursion, lock, publication, durability, or error-mapping policy.

## Goals / Non-Goals

**Goals:**
- Give every migrated raw descriptor one explicit live/transferred/release-attempted lifecycle.
- Preserve an active operation/domain failure over ordinary close failure and retain the close diagnostic.
- Attempt every independent release once even after another release fails.
- Make parent/child handoff mechanically leak-free and retry-free.
- Keep an executable production-tree classification for every explicit close, injected backend release, `fdopen` wrapper, fd-returning `mkstemp`, and subprocess-created fd-owning stream, permitting direct close only for a low-level POSIX primitive, gated shared-owner internal release, or verified ownership handoff.
- Give subprocess stream cleanup one synchronized release claim across concurrent and repeated cleanup paths, without double ownership or closing an fd while a reader can still use its number.
- Encapsulate launch, prepared ownership, internally controlled readers, bounded shutdown, and eventual cleanup in `docker.process.OwnedProcess`, rather than requiring consumers to compose independent lifecycle helpers.
- Distinguish completed shutdown from retained incomplete cleanup and make late outcomes observable without changing an already-delivered operation failure.
- Make filesystem-wrapper selection and lifecycle verification mandatory in documented rules for new descriptor-owning code.
- Separate local process ownership from a launch-configured narrow stop policy, allowing externally defined stop requests without a second shutdown coordinator.
- Deliver generic staged policy/drain/budget/managed-action contracts that can be consumed by later domain wrappers without changing current Docker cleanup semantics.
- Deliver a self-contained ownership/API contract with complete compatibility and release checks.

**Non-Goals:**
- Remove every textual `os.close()` from production.
- Move regular-file validation, hashing, integrity, cache layout, traversal, recursion, lock policy, publication, or durability into `docker.filesystem`.
- Make domain modules import `docker.transactions` merely to reuse its L0 backend.
- Add a generic filesystem, path-policy, retry, recovery, or recursive removal API.
- Add process-tree/group management, stdin handling, PTY support, ownership of arbitrary external reader threads, or migrate the runtime installer to process ownership.
- Put Docker removal, npm domain errors, secret/redaction policy, staging, cache, or publication authority into `docker.process`, or process coordination into `docker.filesystem`.
- Change existing consumer public APIs, persistent data, user-visible domain diagnostics, or success semantics beyond the expressly authorized lifecycle corrections. The only new public foundation surface is the bounded `OwnedStream` wrapper.

## Decisions

### Use `OwnedDescriptor` for every single consumer-owned lifecycle

After a successful raw `os.open`, npm lockfile writing, npm tree hashing, runtime artifact verification, private build-context writing, snapshot destination copy, and artifact-cache temporary creation transfer the fd immediately into directly constructed `OwnedDescriptor(PosixDescriptorOps(), fd, label=...)`. `ValidatedProjectState` likewise stores or delegates to one private `OwnedDescriptor` while preserving its public construction and descriptor access contract. Operations continue to use the live `fd` property.

With an active primary, `CleanupFailures(primary)` runs `owner.close` alongside any independent cleanup such as unlink. On a successful path, `owner.close()` reports a sole close failure while retaining terminal at-most-once state. A bare `finally: close()` is never considered a sole-failure exception because an operation failure may already be active.

This reuses only ownership and close precedence. It does not add regular-file open/read/stat/hash APIs to the foundation. Alternative: add `RegularFileDescriptor`. Rejected because these consumers have different type, ownership, mode, integrity, and domain policies, and only lifecycle is common. Alternative: retain bare success-path or `finally` closes. Rejected because they bypass uniform terminal ownership, and a `finally` close can additionally mask an active failure.

### Make implicit file-object adoption explicit

Every raw fd returned by `tempfile.mkstemp()` or another integer-fd factory transfers immediately to `OwnedDescriptor`. Consumers that need a Python file object construct it with `os.fdopen(owner.fd, ..., closefd=False)`, so closing the file object cannot implicitly release the descriptor and the shared owner remains the sole release authority. File-object flush/close errors remain operation failures; owner release runs afterward through `CleanupFailures(primary)`, making descriptor-close failure secondary and terminal. The migration covers artifact materialization, effective-inventory rendering, and HTTP cache persistence while preserving temporary-name cleanup, publication order, bytes, modes, and domain mapping.

The convergence gate resolves aliases of `os.fdopen` and `tempfile.mkstemp`, treats omitted `closefd` as `True`, rejects consumer `closefd=True`, and requires every fd component returned by `mkstemp()` to transfer to a shared owner before another fallible operation. `closefd=False` is accepted only when the same fd has a proven external shared owner.

### Restore prevalidated stream ownership without a second raw-fd owner

`OwnedStream` in `docker.filesystem.streams` retains only labeled adoption, borrowed live stream access, terminal-state inspection, explicit close, and context-manager cleanup. Validate a non-empty label and callable stream `close` interface and prepare synchronization before transfer. Rejection, including lock-construction failure, leaves the caller's stream untouched; closing a rejected candidate is not adoption. Its constructor must not hide a release interruption or defect behind `ValueError`. Private generic preparation/binding support may be added for process ownership, but is not a public factory, proxy, raw-fd, detach/retry, or process API. It must use the same single owner state machine and have executable transfer proofs.

`OwnedStream.close()` synchronizes the live-to-release-attempted claim and invokes the underlying close outside the claim lock. Repeated, concurrent, or reentrant calls cannot retry, including after ambiguous failure. A terminal claim is not proof of completed close. The process coordinator retains the winning outcome before claiming cleanup completion. Stream access is borrowed and grants no independent close authority; neither the stream nor its `fileno()` receives a second owner. Direct close still has only the existing primitive, terminal shared-owner internal release, and verified handoff categories.

### Encapsulate subprocess machinery in `docker.process.OwnedProcess`

Introduce a reusable process-lifecycle layer with dependencies `consumer → docker.process → explicit docker.filesystem submodules`. It owns one direct child, captured stdout/stderr through `OwnedStream`, internally created readers, cancellation, terminate/kill/reap, and cleanup-result coordination. It has no npm/versioning/transactions/runtime-installer imports or Docker removal, path, redaction, publication, staging, or cache policy. Consumers supply argv, launch configuration, reviewed deadlines/grace, bounded capture parameters and an optional prepared stop policy. Omitting the policy preserves the default local-process contract; a configured policy is not an arbitrary callback replacing shutdown. The runtime installer needs no process-owner import or image-layout addition for this module.

The acquisition entry point is `OwnedProcess.launch(...)`, not wrapping an already-launched `Popen`. Before launch, validate configuration and prepare owner slots, labels, locks/events, tracking and cleanup-continuation capacity. If deferred cleanup needs a worker, its startup/readiness is part of this preparation rather than a fallible action first attempted after shutdown times out. A preparation or factory failure launches no child/acquires no pipes and tears down any already-prepared idle workers through accumulated cleanup. Immediately after a successful launch, each returned pipe is accounted for by that prepared authority before reader configuration, callbacks, or supervisors. Binding to its designated stream owner does not allocate a replacement lock or reconstruct a release authority. Distinguish failed transfer from completed adoption explicitly: if a post-launch binding/setup seam fails, the acquired ledger and already-prepared owner machinery still supply exactly one release authority for every real pipe. Do not solve this by retrying arbitrary constructors, closing a rejected stream in a test mock, or adding consumer-close fallbacks. Supported injected factories provide both captured streams. Missing streams are malformed factory results requiring controlled failure, safe independent release and bounded child cleanup, not successful execution.

The public process surface provides launch, context management, capture, streaming, coordinated shutdown, cleanup-status observation, and bounded `wait_cleanup(timeout)`; concrete policy/result type spellings are implementation details, not license for extra lifecycle APIs. Document this surface and runnable usage in `docs/process-lifecycle.md`; link it from the existing filesystem and assembler guides. Capture returns bounded output and the child result. Streaming supplies byte chunks to the existing domain collector and preserves its callback-isolation guarantees; callbacks do not receive raw pipes or release authority. Borrowed process observation needed by existing adapters grants no independent shutdown ownership. No ownership API for arbitrary external reader threads is introduced. Production readers are cancellation-aware/non-blocking and created/tracked by the process owner; descriptor-less injected streams are a compatibility seam, not a promise to interrupt any blocking Python `read()`.

Use one cleanup coordination state machine and retained failure ledger, not independent implementations in `execution.py` and `lifecycle.py`. An operation interruption is installed before subsequent actions. Every adoption/binding failure, join failure, independent close failure and reaping failure participates in shared precedence: original or first interruption, unexpected defect, original ordinary operation failure, then ordinary cleanup failure. Explicitly declare `OSError` as ordinary for release; classify join/setup defects deliberately rather than catching all `Exception` as ordinary. First adoption failure followed by a second `KeyboardInterrupt` selects that exact interruption with the first failure retained. All independent actions run before raising or reporting authority; no close/join defect skips child reaping.

### Preserve a bounded process result on capture and stream failure

Keep `OwnedProcess.capture() -> ProcessResult` and both successful result types unchanged. The separately authorized streaming extension is `OwnedProcess.stream(callback, *, on_stream_end=None) -> ProcessResult`, with typed `ProcessStream` identities and immutable `stream_outcomes` as specified below. Before either operation delivers an authoritative exception, attach `error.process_result` containing an immutable snapshot of the existing generic `ProcessResult`: bounded raw `stdout`/`stderr` bytes, `returncode`, `timed_out`, the delivered `CleanupResult`, bounded `callback_errors` and immutable `stream_outcomes`. Preserve the authoritative exception's exact identity and type; do not introduce an exception wrapper, new result type, owner output property or lifecycle method. This contract applies to operation, reader, wait and cleanup failures, interruptions and controlled incomplete cleanup originating from capture/stream, not validation or launch failures before collection begins.

Publish the snapshot at the operation delivery boundary with synchronized bounded tail copying and the current undelivered cleanup outcome. A live retained reader must not mutate the copied bytes. `cleanup.complete=False` remains a valid delivered snapshot. Later output, release failures or completion must not replace its fields, mutate delivered exception diagnostics or reattach a newer snapshot to an already-delivered exception; eventual cleanup remains observable through the original owner's status and `wait_cleanup(timeout)`. Existing launch-failure `.cleanup` observation access is unchanged, and launch errors need not carry `process_result`.

The captured adapter projects this supported snapshot into `LifecycleOutcome` on failure rather than reading private owner tails or invoking capture again. Generic bytes are not sanitized public diagnostics: decoding, redaction, bounded note projection and Docker exit/absence interpretation remain domain responsibilities. A streaming snapshot is a bounded raw tail, not a transcript of callbacks; never replay it into the sink or automatically initiate callbacks belonging to a completed stream invocation after its result/exception delivery. A later explicit stream invocation may notify its newly supplied end callback of retained terminal outcomes without replaying output. Preserve incremental redaction, per-stream finalization and abort-safe retained diagnostic tails in the streaming adapter independently of raw snapshot projection.

### Retain typed per-stream outcomes and notify through stream

Add domain-neutral enums in `docker.process`: `ProcessStream` with `STDOUT` and `STDERR`, and `StreamOutcome` with `PENDING`, `EOF`, `READ_FAILED` and `ABORTED`. Each acquired stream transitions once from `PENDING` to exactly one terminal outcome. `EOF` means actual clean EOF before collection cancellation; `READ_FAILED` means read failure, not a redactor or sink callback error; `ABORTED` means collection was forcibly discontinued. Terminal outcomes are not revised by a sibling failure or later cleanup. `ABORTED` does not prove child exit, reader stop or safe pipe release: existing reader barriers and retained ownership remain authoritative.

`stream`'s chunk callback accepts `(stream: ProcessStream, data: bytes)`. Its optional keyword-only `on_stream_end` accepts `(stream: ProcessStream, outcome: StreamOutcome)` and receives terminal outcomes only, never `PENDING`. This deliberately replaces string chunk identities with enum identities; do not add a parallel string compatibility channel or a separate subscription method. All calls happen on the stream invocation's coordinating thread outside state locks. Callbacks remain prompt-returning; ordinary callback exceptions are isolated in the existing bounded `callback_errors`, without retry, while control-flow interruptions follow shared precedence.

Retain outcomes independently of callback registration. For each stream invocation with an end callback, make one terminal notification attempt per stream before that invocation returns or raises, including outcomes established before registration. Synchronize registration, outcome transitions and delivery so concurrent completion cannot lose or duplicate a notification. Deliver chunks assigned to that invocation before the corresponding end notification; clean EOF notifications are prompt and do not await sibling completion. Error/cancellation must not discard a previously established clean EOF. Pending collection is marked `ABORTED` before operation delivery; later reader completion does not revise it or begin an automatic callback. An explicit subsequent stream invocation may deliver retained outcomes to its new callback even after cleanup/result delivery, but must not reread pipes, replay delivered chunks or raw tails, restart cleanup or modify prior results/exceptions. Concurrent invocations use existing operation serialization and per-invocation notification accounting, not additional reader/coordinator ownership.

Extend the existing immutable `ProcessResult` with `stream_outcomes: tuple[tuple[ProcessStream, StreamOutcome], ...]`, containing each stream once in STDOUT/STDERR order. Populate it for capture and streaming success and `error.process_result` failure snapshots from the synchronized outcome ledger; callback delivery failure does not erase the underlying outcome. Delivered fields remain immutable across later observations and subscriptions. This is a field extension, not a new result type or mutable mapping. `PENDING` describes an outcome not yet established, not a reader running or resource released; collection delivery resolves acquired streams to terminal outcomes.

The adapter maps enum identities to its existing domain tags and finalizes each DiagnosticStream with `abort=False` only for `EOF`, and `abort=True` for `READ_FAILED` or `ABORTED`. Preserve the case where stdout clean EOF finalizes an unresolved secret prefix normally before a later stderr read failure; do not finalize both streams using the aggregate process failure. Streaming notification replay for a new explicit subscriber is outcome-only, never byte replay into an already-finalized domain collector. Domain sink callbacks and diagnostics still cannot be initiated by late cleanup.

### Return captured ownership alongside the legacy outcome snapshot

Change only the captured adapter's return contract to `run_captured(argv: Sequence[str], *, policy: LifecyclePolicy) -> tuple[OwnedProcess | None, LifecycleOutcome]`. Keep its input parameters and all `LifecycleOutcome` fields (`return_code`, `errors`, `stdout`, `stderr`). The first tuple element is the single generic owner, not a raw or borrowed `Popen`; do not expose raw pipes to preserve test access. The second element remains the delivered result snapshot, including existing bounded decoding and domain diagnostic projection. Owner status and `wait_cleanup(timeout)` provide later cleanup observation without mutating the delivered outcome or emitting late public callbacks/diagnostics.

Return the owner after successful launch, including when capture or cleanup fails. If launch/setup raises before returning the owner but carries generic cleanup observation access, return that same owner with the mapped failure outcome; never reconstruct ownership. Return `None` when no owner/cleanup observation handle is available, including ordinary pre-acquisition failure. A returned owner does not imply acquisition or execution succeeded; the outcome records the failure. Incomplete cleanup must remain visible through the existing outcome error channel and the owner's observation interface.

The sole production caller, `execution.py::_bounded_docker_rm`, currently ignores the first tuple element and continues interpreting `LifecycleOutcome` for exact existing exit/absence/removal error policy. Audit that caller and tests during migration. Replace test access to returned `proc.stdout/stderr` with owner cleanup observations, while independently checking actual pipe close counts and reader-stop safety through controlled factory fixtures. Keep captured clients on the default local stop policy and do not convert this change into a new Docker wrapper.

Keep `OwnedProcess` strict missing-stream rejection unchanged. Standard `Popen(..., stdout=PIPE, stderr=PIPE)` provides both streams; normal test doubles must do likewise. Treat an injected missing stream as a malformed factory result and report controlled setup failure while releasing every present pipe once when safe and boundedly cleaning up the child. Do not preserve legacy successful execution with missing streams, fabricate replacement streams or expand the generic API for this test seam.

### Expose a domain-neutral launch-selected stop-policy API

This change defines and implements the generic extension contract. Docker operation construction, prelaunch cancellation state, container-control commands, Docker phase mapping and daemon-side status interpretation are out of scope. `OwnedProcess.launch(...)` remains the generic acquisition entry point; no generic prepare/start split, existing-process adoption or Docker subclass API is added.

A later wrapper can select its policy at launch; explicit shutdown, deadlines, context exit, reader failures and partial setup then enter the same local cleanup coordinator. Keep the extension narrow enough that neither a domain wrapper nor a policy can replace shutdown, directly signal/wait/reap the raw child, own external readers or release pipes. Generic tests use local cooperative child fixtures and fake policies, not Docker identities, commands or wrapper states.

Select and validate the policy at generic `launch()`, before acquiring the main child. Prepare its tracking and any continuation capacity there as part of the existing preparation contract. The extension is a small generic lifecycle protocol: bounded stop-request initiation/observation, optional escalation/finalization stages and retained action outcomes, with shutdown reason and read-only child observation as needed. It grants no raw `Popen`, pipe, external-reader, direct wait/reap or release authority. The generic coordinator, not the policy, decides stage transitions, applies shared precedence, performs local waits/fallback, confirms reader-stop barriers and publishes outcomes. Local natural completion/finalization is distinguished from cancellation/failure so successful captured helper clients do not invoke unnecessary external stop actions; required external cleanup actions remain eligible even if the local child has already exited; local resource completion never proves externally controlled work stopped.

Supported policy requests are nonblocking initiation/observation of explicitly owned, deadline-bounded operations, not arbitrary blocking Python callbacks. A stalled managed action must not occupy the sole coordinator or prevent permitted fallback and safe independent cleanup. An action that launches an auxiliary child uses a separate OwnedProcess with the default local policy and one OwnedStream per pipe, capped by its stage/parent remaining budget; domain-specific recursive policy mapping is not part of this generic contract. Failed or pending auxiliary setup/cleanup retains its owners and observation handles. Arbitrary blocking Python policy callbacks have no forcible-stop guarantee and are not the supported extension surface.

Policy plans may describe bounded stop-request, optional escalation, finalization and natural-child-wait stages while only the coordinator executes local terminate/kill/reap. A staged external-stop plan permits local fallback after its final external stage fails/expires; a default local-stop plan retains its current local behavior. The contract must also permit existing adapters to preserve their characterized local-stop → managed domain cleanup → local wait/reap ordering without giving the adapter raw child authority. Implementing a new Docker cooperative policy is not required to prove either generic mode.

Validate finite positive configured stage caps and a local-cleanup reserve before main acquisition; their sum must fit the supported total budget. Start each absolute monotonic phase clock before managed-action initiation, include both action execution/observation and subsequent child waiting, and cap every wait by the phase and remaining total deadline. Explicit failure advances immediately; early completion cannot enlarge another phase's cap. Repeated/concurrent calls do not restart clocks. Keep stop requests separate from reader cancellation so a configured bounded drain can precede cancellation and safe release. Default local policies and behavior-preserving adapters retain their supported total bounds. Concrete Docker stage settings, daemon-side grace conversion and remote-state evidence are outside this generic API's scope.

Distinguish operation/stop-request cancellation from reader cancellation. A policy selecting bounded draining does not immediately abort readers; they continue draining into bounded tails/spooling without depending on a prompt consumer callback or an unbounded queue. Domain callbacks remain isolated and receive bytes, not ownership. Reader cancellation follows drain completion or its allocated expiry; an expired join never permits releasing a live reader's descriptor.

Generic cleanup completion confirms reaped owned local resources, stopped readers, terminal release attempts and published winning outcomes, including retained managed action resources. Retain action observations separately without deriving any external-work success from local child exit. Domain consumers interpret those observations; the generic owner does not produce Docker confirmation/absence/unavailable diagnostics. Every policy stage is at most once and concurrent callers share its outcomes.

Required lifecycle control actions are internal cleanup operations, not user-facing callbacks. Initiate the stop/fallback/removal stages within the shared reserved budget before delivery; after delivery, retain and observe already-started action/helper outcomes and safely release resources without new domain output, user callbacks, budget resets or retries. Late action failures do not mutate delivered results or exceptions; domain interpretation must not retroactively replace delivered outcomes.

Alternatives rejected: replacing shutdown through inheritance (duplicates ownership/precedence); configuring stopping only around an explicit caller invocation (missed autonomous triggers); unrestricted whole-shutdown callbacks (no enforceable independent cleanup); importing domain commands/identities into the generic layer; independent full grace budgets per managed action.

### Separate bounded shutdown from eventual cleanup completion

The lifecycle is prepared → launched → running → shutting down → cleanup complete or shutdown incomplete → cleanup complete. Cleanup complete means the child is reaped, supported readers have stopped, every acquired pipe has its terminal release attempt, and all winning outcomes are published; it does not mean every release succeeded. Repeated/concurrent shutdown joins the same coordination and outcome rather than restarting budgets, reaping twice, re-adopting streams, or duplicating diagnostics.

Operation cancellation is recorded promptly; a configured stop policy may select a bounded final drain before reader cancellation. The generic contract does not require a cooperative Docker sequence or fixed soft/hard stages. The default local policy retains its supported behavior. Joins, policy actions, child termination/reaping and safe independent releases use accumulated actions and the same monotonic budget compatible with existing consumer deadlines/grace. A join interruption is retained without skipping sibling cleanup or reaping. A descriptor-backed pipe cannot be released while its reader can still access it. Process exit alone, `is_alive()` assumptions without the tracked reader barrier, or a timed-out join do not authorize close. Descriptor-less compatibility readers may require owner close to unblock; they never justify closing production descriptors beneath live readers. The existing Docker terminate-CLI/remove/reap sequence remains a compatibility requirement in this change; replacing it with cooperative container stopping is out of scope. Removal remains a domain action and its failure cannot bypass generic process cleanup.

When bounded shutdown cannot finish, report `shutdown_incomplete` with a retained cleanup handle/result, never successful cleanup. Hold the same owners and worker references in a per-process continuation prepared before launch, with no hidden global ownership registry or GC authority. Deferred cleanup releases each pipe only after its reader has actually stopped, retains late failures once, and publishes completion. `wait_cleanup(timeout)` observes/waits without retrying close or restarting shutdown; after timeout the state and responsibility remain incomplete. If a reader never stops, ownership remains retained indefinitely and cleanup is not claimed complete. Generic bounded caller waiting does not imply Python can stop arbitrary threads or forcibly bound arbitrary injected `close()` calls.

Context exit uses the same shutdown path. Without an active failure, incomplete shutdown raises a controlled incomplete-cleanup error carrying observation access. With an active failure, apply shared precedence to failures known before delivery and retain the incomplete-cleanup observation on the authoritative error; an incomplete-shutdown timeout is ordinary and must not mask an existing interruption. A launch failure requiring deferred cleanup likewise carries observation access even though no process owner was returned. Adapters preserve their established list/outcome/error fields, with the explicitly authorized `run_captured` first-element replacement by `OwnedProcess | None`, and project a bounded sanitized incomplete-cleanup diagnostic instead of adding raw generic notes to public channels. They keep the continuation alive independently of a caller retaining the generic handle.

Once an operation result or exception has been delivered, later cleanup failures are observable only through the retained cleanup result. They do not mutate the delivered result, emit late domain output/callbacks, or retroactively replace its authoritative exception. Domain sanitization remains in adapters; raw internal failure identity may be retained in generic results but no unbounded diagnostic/output retention is added.

Alternatives rejected: caller-composed preparation/join/reap helpers (too many invalid combinations); `OwnedProcess(existing_proc)` as the acquisition API (leaves the launch-to-adoption gap); putting process machinery in `docker.filesystem` (violates its authority); raw-fileno adoption, raw-close fallbacks or another direct-close category (double ownership/unsafe retries); accepting arbitrary external reader threads (no enforceable stop contract); always closing after a join timeout (fd-reuse hazard); always waiting indefinitely (violates bounded return).

### Use an accumulator plus terminal state for multi-descriptor owners

`docker.versioning.build_cache.BuildCacheState`, the authoritative class returned by `open_build_cache_state()`, privately owns one `OwnedDescriptor` for each of its five descriptor fields: `persistent_fd`, `blobs_fd`, `tmp_fd`, `markers_fd`, and `transactions_fd`. Its existing constructor, `paths` field, five integer descriptor fields, signatures, and return identity remain compatible. `close()` first makes aggregate ownership terminal or detaches its complete owner collection, then submits every `owner.close` action to one `CleanupFailures(None)`. A repeat close is a no-op. This prevents skipped later cleanup and unsafe retries after ambiguous close failure.

Alternative: stop at the first close error. Rejected because descriptors are independent cleanup actions. Alternative: retain raw integers plus a second bespoke terminal ledger. Rejected because the shared owner already supplies the required state machine; private owners avoid duplicating it.

### Migrate unsafe directory handoff to `DirectoryDescriptor` where complete semantics match

Build-cache path walking and `_bootstrap_constructor_project_lock_parent()` in `docker/versioning/build_cache.py` use `DirectoryDescriptor.open_secure_path`, `open_directory`, `create_directory`, or `open_or_create_directory` only where basename, owner, mode, and no-follow contracts match exactly. Build-cache continues to derive paths, decide missing-component creation, validate cache-specific state, map `BuildCacheError`/`BuildTransactionError`, and own recursion and lock policy.

If a handoff cannot use `DirectoryDescriptor` without changing an established validation or pre-transfer ownership contract, it uses `OwnedDescriptor` as an explicit ledger. The child becomes owned before parent release; the parent becomes terminal before close; a parent failure triggers exactly one child release.

Alternative: wrap the existing parent close in `CleanupFailures(None)`. Rejected because precedence alone cannot repair an untracked child or prevent retry of an ambiguously failed parent close.

### Preserve correct direct-close categories

The implementation starts from an executable inventory and keeps these categories:

- **primitive:** `PosixDescriptorOps.close` and `PosixFileOps.close` remain direct raw delegates;
- **shared-owner internal release:** `OwnedDescriptor.close()`, `OwnedStream.close()`, or an equivalent shared-owner implementation may invoke its injected close operation only after making ownership terminal; stream release additionally requires a synchronized claim; executable gates reject the same call shape in ordinary consumers;
- **owned lifecycle:** every single consumer-owned release, including success paths, lifecycle methods, fds returned by `mkstemp`, and descriptors exposed through file objects, delegates to the shared owner;
- **file-object wrapper:** `fdopen(closefd=False)` is permitted only while a proven shared owner retains the wrapped fd; omitted or true `closefd` is forbidden in consumers;
- **already fd-owning stream:** subprocess-created file objects transfer release authority to `OwnedStream`; their underlying file-object close is a shared-owner internal release, not a fourth direct-close exception. This does not permit consumer `fdopen(closefd=True)`;
- **protected cleanup:** active-primary or multiple independent releases use `CleanupFailures` with one or more shared-owner `close` actions;
- **ownership handoff:** a direct close is permitted only after the parent is terminal and the child is tracked before the potentially failing call.

There is no out-of-scope classification for production consumer-owned descriptor release, whether explicit or hidden behind a file object: every such lifecycle discovered by the repository inventory is migrated to the shared owner/cleanup lifecycle.

The convergence gate resolves symbol origins rather than matching spellings for explicit closes, `os.fdopen`, and `tempfile.mkstemp`. It follows aliased `os` imports, `from os import close as ...`, transitive local assignments of close callables, aliases of backend objects, and injected descriptor-operation values through parameters, constructor fields, and local assignments. A call whose resolved origin is the POSIX close primitive or an injected descriptor backend's `close` method is classified regardless of variable name; unresolved close-like calls in the audited production tree fail closed until explicitly proven non-descriptor. Fixtures cover each alias path, so renaming `os`, `close`, `ops`, `self._ops`, or an intermediate callable cannot evade the gate.

### Keep failure translation at domain boundaries

`docker.filesystem` continues to propagate raw ordinary close errors. Npm tree and lockfile helpers preserve their established boundary distinctions. `_write_lockfile()` maps staging-file open failure to `LockedNpmError("unsafe_staging_path", ...)`, and `_hash_file_entry()` maps file-entry open failure to `LockedNpmError("tree_type_mismatch", ...)`; both retain the original `OSError` as cause. Unsafe tree type also remains `LockedNpmError`. Stat, read, write, hashing, and close failures propagate raw, and migration does not reclassify those operational failures. Build/versioning boundaries retain their existing error types and wording. With an active primary, the raw close error is secondary. Without one, existing mapping or propagation remains unchanged except at `open_verified()`: its formerly escaping sole close `OSError` is intentionally mapped to `InstallError(f"cannot close artifact at {_path}: {exc}")` with that `OSError` as the direct cause, so callers and the CLI/result path use their controlled installation-failure behavior. Process-control exceptions remain unwrapped and follow shared precedence.

Alternative: make `OwnedDescriptor.close()` produce transaction/domain errors. Rejected because the foundation is domain-neutral and cannot select those classifications.

### Establish durable developer rules and executable enforcement

## Risks / Trade-offs

- **[Risk] A broad search-and-replace wraps handoff closes and breaks ownership sequencing.** → Require the executable inventory and per-site classification before edits; migrate consumer releases to owners while preserving justified primitives and handoff operations.
- **[Risk] Constructing `OwnedDescriptor` after open can strand an fd if local argument preparation fails.** → Validate/compute labels and backend before `os.open`, then transfer immediately with no intervening operation.
- **[Risk] Directory foundation validation differs from a legacy domain's pre-transfer contract.** → Characterize validation order and ownership first; use `DirectoryDescriptor` only when complete semantics match, otherwise use `OwnedDescriptor` ledger mechanics.
- **[Risk] Close fault injection no longer patches module-local `os.close`.** → Inject `DescriptorOps` explicitly in new tests and retain compatibility seams only where existing public tests require them.
- **[Risk] A terminal multi-fd owner changes publicly observable attributes.** → Preserve public fields/signatures and implement terminal ownership privately; add compatibility introspection tests.
- **[Risk] Domain messages drift when raw close failure becomes secondary or when runtime sole close gains its authorized mapping.** → Pin exact primary type/message/cause and secondary diagnostics, plus the new close-specific `InstallError` and CLI/result output, before migration.

- **[Risk] A stream wrapper and an integer-fd owner close the same resource.** → Give already fd-owning streams only `OwnedStream`; prohibit raw-fileno adoption and raw-close fallbacks in tests and the ledger.
- **[Risk] Concurrent close is claimed once but blocks on a live buffered reader.** → Keep the claim lock narrow, use owner-controlled non-blocking readers in `docker.process`, and require real-pipe deadline/fd-reuse tests before migration is accepted.
- **[Risk] A post-launch constructor failure strands a pipe or rejection steals caller ownership.** → Prepare fallible owner/coordinator inputs before launch, prove the transfer boundary and acquired ledger, and inject actual lock/binding failures instead of self-cleaning adoption mocks.
- **[Risk] A join interruption skips reaping or a timed-out reader is closed while live.** → Accumulate fallible joins and independent cleanup; retain the owner with a prepared continuation until the reader-stop barrier is satisfied.
- **[Risk] Incomplete cleanup is mistaken for success or a late failure rewrites a delivered error.** → Expose incomplete status and bounded cleanup-result observation; publish late failures only there, with adapters controlling bounded sanitized diagnostics.
- **[Risk] A permanently blocked injected reader retains resources forever.** → Document this explicit incomplete state, reject arbitrary external reader ownership, and do not trade fd safety for a false completion guarantee.
- **[Risk] A timeout winner's close failure is lost or a losing cleanup returns too soon.** → Share the owner pair and await/publish the winning cleanup outcome without repeat close or duplicate diagnostics.
- **[Risk] Shared diagnostic attachment leaks unsanitized subprocess failures.** → Characterize and retain domain-local bounded redaction for all public notes/results, including unexpected defects and interruptions.
- **[Risk] A future policy misses autonomous triggers or overrides local safety.** → Configure bounded stages before acquisition, keep one coordinator and test all triggers without domain imports.
- **[Risk] Action execution consumes fallback time or phase caps are restarted.** → Include action execution and child waiting in each phase clock, reserve local cleanup under the supported total bound and observe owned auxiliary clients nonblockingly.
- **[Risk] Reader cancellation loses final output or callback backpressure stalls shutdown.** → Separate stop request from reader cancellation; bound drain/tails/spooling and preserve abort redaction without relying on consumer callback progress.
- **[Risk] Generic local completion is treated as external success.** → Retain managed action observations without interpreting external-work state; domain-specific interpretation is deferred.
- **[Risk] The stop-policy extension reintroduces primary/publication races.** → Keep the active operation as `CleanupFailures(primary)`, preserve the first recorded interruption, and refresh the undelivered outcome under lock immediately before delivery; replay the exact-gap barrier regressions across policy stages.
