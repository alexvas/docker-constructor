### Ownership and failure rules

1. Prepare the HTTP response adapter and its single `docker.filesystem.streams.OwnedStream` before `urlopen`. Bind a returned response or caught HTTPError before reads, headers/status inspection or formatting. Bind the HTTPError object itself, not its `fp`, socket or `fileno()` separately. An absent body must not fabricate a resource close.
2. Launch the probe child only through one `OwnedProcess`, with KILL mode selected before acquisition. The owner prepares/owns captured pipes; the parent never reads, signals, waits/reaps or releases borrowed child/pipes independently. Inside the child prepare one listener adapter/`OwnedStream` before server acquisition and bind before inspection. Do not adopt accepted stdlib-owned streams again; each newly explicit stream needs its own sole `OwnedStream`. SIGKILL and watchdog hard exit intentionally skip Python finally blocks: verify kernel resource reclamation at actual child exit, not fictitious Python close calls.
3. Only the named terminal shared owner may release an adopted resource. Do not also use the resource's native context manager, a borrowed close alias, garbage collection or a newly reconstructed owner. A release failure/interruption is an at-most-once attempt, NOT permission to retry.
4. Use `docker.filesystem.cleanup.CleanupFailures` semantics: first control-flow interruption, then first unexpected cleanup defect, then original ordinary operation failure, then first ordinary cleanup failure. Preserve the selected exception object's identity before an existing domain projection. Retain displaced failures as secondaries and attempt every independently safe cleanup once. HTTP release ordinary failures are `OSError`; do not classify all `Exception` values as ordinary merely to suppress defects. Preserve existing broader domain classifications only at their characterized boundaries.
5. Buffered mapping: normal acquisition/read OSError maps to the established 503 response; a successfully processed HTTPError returns its own status/headers/body; failures while reading the HTTPError handler remain raw. A sole ordinary release failure maps to 503 on either response path. Never include secondary-cleanup notes in the public 503 body.
6. Streaming acquisition HTTPError remains the exact primary over ordinary error-response release failure. EOF is successful only after release succeeds. `generator.close()` normally consumes GeneratorExit; `throw(interruption)` preserves the interruption identity. An ordinary release failure during GeneratorExit must not replace GeneratorExit. Merely dropping an externally retained iterator provides no deterministic cleanup guarantee.
7. The artifact consumer must close its actual acquired iterator if its close attribute is callable. Capturing that callable for invocation inside protected finalization is valid, unlike aliasing an adopted response's borrowed close to bypass its owner. Plain iterators without close remain valid inputs. Keep a strong external reference in early-consumption-failure tests so GC cannot make a missing finalizer appear correct.
8. Probe stop requests immediate SIGKILL for a live child through the owner without SIGTERM/graceful waiting. Attempt reap, pipe-reader/release settlement and collector completion within one five-second total observation budget; do not require completion before returning valid finished gateway checks. Ordinary cleanup failure/incompleteness produces one fixed sanitized parent-side warning and preserves the diagnosis; active startup/check errors retain ordinary cleanup failures secondarily. Unexpected defects/control-flow interruptions still obey shared precedence and are not downgraded. Generic `OwnedProcess` cleanup may be complete only after actual reap and safe resource settlement; retain its same reachable owner/collector/continuation otherwise, with no new budget, independent kill/reap, last-reference loss or GC release dependency. Handle bounded `CleanupIncomplete`/context exit at the networking boundary without restarting waits or turning completed checks into failure. Reap an already exited child without redundant signalling. Uninterruptible kernel waits can leave a child/random port/pipe/collector behind; warn honestly, do not wait indefinitely or falsely claim full cleanup.
9. The child's independent watchdog starts before bind, uses one absolute monotonic 1200-second lifetime and calls `os._exit(124)`, not `sys.exit`, without deadline resets. It remains required with socket timeouts and is not a guarantee that a stopped/GIL-blocked process can schedule it. Configure the child listener timeout and `HTTPServer.timeout` to one second in a repeated `handle_request()` loop, not serve_forever (which ignores that field). Set each stdlib-owned accepted connection's read/write inactivity timeout explicitly to three seconds before parsing/response I/O without adopting its fd again. Idle timeout continues serving; accepted timeout cleans only that request and continues serving. The fixed three-second accepted limit is independent of, and can expire earlier than, client probe_timeout (unchanged 1–300 seconds/default 3 and wget forwarding). This intentional slow-client restriction is an authorized preservation exception: total requests over three seconds may succeed with shorter gaps, while a gap over three closes that connection. It is not a total candidate deadline and must not change or make claims about existing client retries.
10. Each new acquisition, binding/transfer, wrapper and cleanup branch needs operation-plus-close, sole-close, interruption and repeated-cleanup coverage. Add independent-resource, handoff and concurrency cases where the supported path needs them, including generic process shutdown concurrency but not a new concurrent probe API. Tests that add real resources must release/reap them deterministically even when assertions fail.
11. Readiness is exactly one flushed UTF-8 JSON line `{"port": <integer 1..65535>}` of at most 256 bytes including newline, with a ten-second parent wait. Collect through one tracked `owner.stream` thread and prompt callbacks, not a borrowed-pipe read or a second capture. Ordinary callback exceptions are diagnostic-only: store/notify protocol failures explicitly. No Docker work or unbounded waits in callbacks. Production `HostProbeServer` provides private `_check_health() -> None` from stored collector outcomes: return when no failure is known, raise the recorded failure otherwise, with no extra HTTP request, borrowed-child polling or pipe read. Preserve `_host_probe_factory` and DTO/public signatures. Diagnose resolves it via getattr with a private missing sentinel: absence means unknown (no fabricated health/failure/warning), present non-callable means TypeError. Existing start/stop-only injected fakes remain valid without adding a mandatory method. After start, invoke the optional check before each candidate, after its command and once immediately before final teardown; do not health-check after requesting SIGKILL. Any known startup/protocol/early-exit/watchdog failure blocks diagnosis success; expected requested -SIGKILL does not.
12. The intended lifetime budget is 10-second readiness + 3 candidates × (300-second HTTP timeout + 60-second Docker overhead allowance) + 60-second margin = 1150 seconds, below the 1200-second production watchdog cap. The overhead/margin numbers are planning allowances, not new enforced Docker-command deadlines. It is not a bound on the existing unbounded `docker run` startup/image delays. Do not redesign that runner here or promise the watchdog cannot expire during an arbitrarily slow command. Expiry means diagnosis failure; tests inject a short private lifetime and must not sleep 20 minutes. Keep watchdog independent of parent stop/collector and do not extend it on requests.
13. Warning delivery has one concrete private boundary: `_warn_probe_cleanup()` in `docker/networking.py` submits WARNING to logger `docker.networking.probe_cleanup` with exactly `probe cleanup not confirmed; temporary resources may remain`, no formatting payload/exception/stack data. Only the controlling diagnosis thread calls it after cleanup observation and before return/failure propagation; mark warning-attempted before the call, skip clean teardown and never retry. Catch reporting `Exception` inside the helper without fallback; do not catch control-flow BaseException or change cleanup classification. Surrounding shared precedence must preserve a pending first interruption if reporting raises another. Do not add public parameters/DTO fields, handlers/root configuration, queues or reporting threads. Background collection/continuations keep internal observations only, with no warning callback/presentation sink and no late output/mutation. Bounded means fixed record size and one submission, not handler runtime; arbitrary configured handlers may block beyond the five-second cleanup observation budget or route records themselves. Do not promise a hard end-to-end return deadline or direct stdout delivery controls over application handlers.
