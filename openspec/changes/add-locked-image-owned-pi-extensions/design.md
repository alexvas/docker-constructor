## Context

Managed extensions currently use reviewed per-version runtime artifact catalogs, host runtime materialization, per-package mounts, and a protected startup installer. `locked-npm-environment-assembly` already provides the pinned, script-free, host-evidenced assembly boundary required for a complete npm closure. Archived `materialize-build-artifacts-on-host` provides the immutable named-context and BuildKit-boundary pattern. `add-durable-filesystem-transactions` provides shared owner-private locks, explicit regular-file contracts, and a canonical JSON codec. This change consumes those primitives while owning the complete closed versioned schemas and recovery protocols for its sync-lock journal and settings sidecar, including its domain-owned multi-target and compare-and-swap adapters.

## Goals / Non-Goals

**Goals:**
- Make managed extension roots, closure, update, delivery, and mutation ownership explicit.
- Preserve user-owned Pi settings entries while making managed roots deterministic and image-owned.
- Keep all npm assembly and network activity outside BuildKit and runtime.

**Non-Goals:**
- Support managed-extension runtime version overrides, unreviewed lock edits, runtime npm installs, registry access at runtime, or selective transitive-package activation.
- Change the consumer-neutral assembler cache format or make Pi user settings constructor-owned wholesale.
- Guarantee absence of transient cross-origin resolver traffic, observe or authorize each npm redirect hop, or provide a network sandbox/egress allowlist for lock synchronization.

## Decisions

### Use exact TOML roots and one checked-in lockfile
TOML declares only exact managed root package/version pairs. The prerequisite-owned closed `[build.stages.base.node]` record already requires exact `node_version` and `npm_version` values alongside its reviewed image tag and digest. This change reuses rather than introduces those fields; they remain the sole reviewed expected versions for resolver and assembler verification; image tag or metadata never implicitly defines npm version. A single checked-in lockfile v3 records the complete reachable closure and must match those roots exactly. Closure validation starts from the exact roots, follows every dependency edge, rejects absent package entries and incomplete registry metadata, and keeps transitive entries distinct from selectable roots.

Alternative considered: keep a catalog for every override-reachable version. Rejected because it recreates runtime selection and cannot make arbitrary closure combinations reproducible.

### Separate root-version discovery from lock resolution
Ordinary `check-deps` checks managed Pi extension roots through a dedicated version-only provider whose sole authority is `https://registry.npmjs.org/`. It requests unscoped metadata from `/<name>` and scoped metadata from `/@<scope>%2F<name>`, compares each exact reviewed root with the latest eligible stable version, and may suggest only a replacement exact root version. The provider uses the protected Constructor metadata transport through a closed explicit-input boundary: it receives no npm environment/configuration, ambient HTTP authentication, `.netrc`, or cookies; constructs no authorization or cookie headers; accepts optional proxy/CA inputs only through separately validated credential-free policy; and validates bounded redirects against fixed origin `https://registry.npmjs.org:443` before follow. It does not invoke npm, read or resolve transitive lockfile closure data, mutate the lockfile, fetch or reconcile tarball URL/SRI metadata, or access a runtime catalog, projection, or artifact cache. Authority or metadata failure yields `unavailable` without custom-registry or removed-runtime-artifact fallback.

Top-level `sync-lock` is a separate mutation-capable orchestration command, not an extension of ordinary provider reconciliation. It invokes no ordinary update provider or metadata request and changes no reviewed roots. It discovers Constructor-managed lock owners in deterministic order; initially the managed Pi extension `package-lock.json` is the only registered owner. Every owner defines preflight, candidate generation, candidate validation, target path, and prior-byte inputs. All owner preflights must succeed, then every candidate must be generated and fully validated before any checked-in lock changes.

Publication is one durable logical transaction over the complete owner set. It uses the shared owner-private lock, durable-I/O, and versioned journal envelope from `add-durable-filesystem-transactions`, then supplies a domain-owned multi-target adapter rather than treating the base single-authority transition as multi-file atomicity. The adapter records prior bytes and fingerprints, candidate identities and fingerprints, validated target paths, backups, and enough phase/evidence state to distinguish complete prior, partial replacement, and complete candidate generations. Failure before commit changes no lockfile. Interruption during a future multi-file commit is recovered by completing the entire validated candidate set or restoring the entire prior set; a final partial publication is forbidden. Staging, journal, and prior-byte backups are cleaned only after durable completion, while separately owned persistent caches remain outside the transaction. With one owner, the same adapter reduces to one-file atomic replacement without a separate transaction implementation.

The managed-extension owner preflight validates closed inventory schema, exact root declarations, reviewed Node/npm pins, and a safe checked-in lockfile path, but deliberately does not compare current TOML roots with the existing lock or validate that lock's closure. This permits an expected repair state after a manual root edit leaves the checked-in lock on prior roots; ordinary `validate` and `build` continue to reject that drift. The owner creates private staging, starts the reviewed digest-pinned Node image, verifies `node --version`, then verifies `npm --version`; only after both assertions succeed may it render resolver inputs, invoke npm, or permit resolver network access. Post-resolution validation parses only the staged candidate, requires exact correspondence with current TOML roots, and validates its complete reachable closure, SRI, and resolved origins. The intended workflow is ordinary root-version discovery, manual root edit, `sync-lock`, review, and rebuild.

### Resolve lock candidates independently of assembly
The managed-extension lock owner owns dependency resolution and candidate generation under `sync-lock`. Before starting the resolver, it applies only owner preflight—closed schema, exact roots, reviewed toolchain pins, and safe lockfile location—and does not require root matching or closure validity from the existing lockfile. It then starts the inventory-pinned Node image by reviewed digest and first runs `node --version`, comparing it only with reviewed `node_version`; a mismatch stops before any npm command or resolver network access. After Node succeeds, it runs `npm --version`, comparing it only with reviewed `npm_version`; a mismatch stops before npm installation or resolver network access. Only after both checks succeed does it deterministically render a minimal temporary `package.json` from canonically sorted exact roots in private staging and invoke exactly `npm install --package-lock-only --ignore-scripts --no-bin-links --no-audit --no-fund --registry=https://registry.npmjs.org/`. That public registry is the only initial registry Constructor configures, and accepted candidates may record only that registry's HTTPS origin for reachable packages; custom registries and scope-specific registry mappings are unsupported. This configuration and lockfile postcondition does not constrain opaque transient redirect traffic inside npm. The checked-in lockfile is never mounted as writable resolver output. The staged `package-lock.json` is the only candidate eligible for publication.

Resolver execution receives only the existing resolved credential-free proxy and enabled corporate CA projection. It uses an isolated temporary npm user config and an empty global config; host, project, user, and global `.npmrc` files are neither scanned nor mounted, and npm configuration environment variables are removed without interpreting their contents. The fixed argv registry therefore cannot be overridden by `NPM_CONFIG_REGISTRY`, `NPM_CONFIG_USERCONFIG`, scope-specific environment/config keys, or analogous ambient inputs. The synchronization owner checks only whether known ambient npm files or npm configuration variable names are present, without reading file contents or variable values, and emits a prominent warning that the detected inputs are ignored. When none are present, it emits no such warning. Credential preflight applies only to inputs Constructor actually projects into the resolver, including the fixed registry URL and credential-free proxy/CA policy; it does not claim to discover credentials in ignored files or discarded environment values. Command display, logs, exceptions, and candidate data redact projected proxy endpoints and machine-local trust paths. Lifecycle scripts remain disabled even when package metadata declares them.

Redirect following is internal to the pinned npm client used by `npm install`; Constructor does not observe each hop and does not claim to validate a redirect target before npm sends the next request. The guaranteed boundary consists only of the fixed initial registry argv, isolated npm configuration, validated projected inputs, and post-generation candidate validation. It is not a network sandbox: absence of transient cross-origin requests, per-hop observation, and redirect authorization are explicit non-goals without a separate egress-control mechanism. The candidate passes lockfile-v3 parsing, exact root comparison, complete reachable-closure validation, registry metadata validation, and SRI validation before durable atomic replacement. Every reachable registry package must have a credential-free HTTPS `resolved` URL with normalized origin `https://registry.npmjs.org:443`; custom origins, userinfo, and HTTP URLs are rejected even though this postcondition cannot prove that npm made no transient redirect request. Exceptions, signals, and cancellation use one cleanup path that removes the temporary manifest, temporary npm configuration, candidate, and private staging while preserving the prior checked-in lock byte-for-byte. Persistent download caches have separate ownership and survive synchronization cleanup.

This boundary deliberately differs from `locked-npm-environment-assembly`: the synchronization owner resolves dependencies and generates a candidate lock; the assembler accepts only an already reviewed lock, receives the same prerequisite-owned reviewed `node_version` and `npm_version` solely as verification inputs, performs its fixed `npm ci`, validates and publishes the installed tree and evidence, and never resolves updates or rewrites the lockfile. It neither derives expected versions from image metadata nor owns a second expected-version configuration.

Alternative considered: ask the assembler to create or update the lockfile. Rejected because assembly is a reproducibility check over approved inputs; giving it resolution ownership would conflate reviewed-source mutation with deterministic installation.

### Build the complete closure before Docker
The constructor invokes the shared assembler before Docker, validates its tree/evidence, then imports the closure through the existing immutable named context and copies it to `/opt/pi-extensions`. BuildKit and container startup have no npm install or network path.

Alternative considered: run `npm ci` in BuildKit or at entrypoint. Rejected because it weakens host evidence, cache ownership, and reproducibility.

### Remove runtime overrides and artifact mounts
Managed extension version changes are reviewed source changes: edit roots, run `sync-lock`, review, rebuild. `run` rejects the retired override form. Runtime artifacts, projections, mounts, installer DTOs, verification, cleanup, and cache paths are removed for managed extensions.

Alternative considered: offline runtime image selection. Rejected because it requires building and selecting multiple reviewed closures and creates a separate image-selection product outside this change.

### Reconcile settings through a constructor-owned sidecar
The reconciler reuses the shared lock, explicit regular-file contracts, and canonical JSON codec but owns the settings-sidecar schema, recovery protocol, and a settings-specific compare-and-swap adapter: fingerprints are revalidated immediately before replacement, a newer external user edit is a conflict rather than overwrite authority, and recovery distinguishes Constructor's prior/intended pair from unrelated state.

For each reviewed root, the reconciler derives one canonical absolute local package source: `/opt/pi-extensions/node_modules/<name>` for an unscoped root and `/opt/pi-extensions/node_modules/@<scope>/<name>` for a scoped root. It inserts that exact string into `settings.json.packages`; it never registers the common `/opt/pi-extensions/node_modules` directory or any transitive package. The sidecar stores active constructor ownership in a `managedEntries` collection mapping each reviewed root identity to its exact canonical path, separately from `suppressedBaselines`, which retain complete user-owned JSON entries and restoration metadata. A path-like user entry is not constructor-owned without the corresponding ownership record.

Each reconciliation computes the desired root/path set and idempotently adds missing constructor-owned entries, retains exactly one correct entry, replaces an obsolete constructor-owned path, and removes the owned entry when its root disappears. These changes participate in the same prepared-sidecar, settings replacement, finalization, conflict, and recovery transaction as duplicate suppression/restoration. Reconciliation acceptance verifies Pi package discovery loads each registered root's resources and resolves its transitive imports from the shared image-owned closure; successful JSON mutation alone is insufficient.

The settings reconciler is the sole owner of `~/.pi/agent/settings.json` duplicate handling; the Pi wrapper never edits or diagnoses settings state. A duplicate is only a user `npm:` source whose normalized package name equals a managed root name, ignoring version. Git/local sources are never suppressed by name inference. The constructor-owned `~/.pi/agent/docker-constructor-managed-extensions.json` sidecar is versioned and ownership-marked. Each suppression record stores the managed package name, the complete original JSON value of every suppressed entry (including object-form filters and extra fields), and placement anchors for its immediately surviving neighbors plus a fallback index. It also stores a transaction journal with operation, phase, and expected pre/post settings fingerprints. Suppression publishes a durable prepared sidecar record, then acquires a settings lock or performs compare-and-swap revalidation immediately before atomically replacing settings without qualifying entries; a mismatch retries from current settings or returns a recoverable conflict. It then durably finalizes the sidecar; restoration uses the same protocol in reverse. Recovery finalizes post-state, discards pre-state, and preserves active settings plus reports a conflict for any third state caused by user edits. Multiple duplicate npm entries retain their exact order in the sidecar. Restoration uses surviving anchors, then fallback index, never overwrites an equivalent active user npm entry, and never restores formatting bytes rather than the original JSON value. Diagnostics show suppressed baseline entries separately from the effective managed resource. The image-owned read-only closure at `/opt/pi-extensions/node_modules` and writable user npm store at `~/.pi/agent/npm` remain physically separate for package/module resolution and mutation; no mount, copy, link, reconciliation, or cross-store package satisfaction crosses that boundary.

### Guard documented mutations at the command boundary
`/usr/local/bin/pi` classifies only the documented forms owned by this change: `list`; install from canonical npm, git, raw URL, absolute path, or relative path; remove of a canonical npm source; bare and selected update forms `--all`, `--extensions`, `--models`, `--self`, `--self --force`, canonical npm source, and `--extension` plus canonical npm source. It does not infer aliases, reorder argv into recognized semantics, inspect unknown commands for mutation-like markers, or fail closed for unlisted forms. Every unlisted command or argv shape is forwarded unchanged to Pi.

The wrapper is an additional command boundary, not a replacement for the prerequisite-owned Pi launcher. The evidence-verified `/opt/pi/bin/pi` produced by `materialize-build-artifacts-on-host` remains unchanged as the real executable. The final user-visible `PATH` places `/usr/local/bin` before `/opt/pi/bin`, so ordinary `pi` lookup selects the wrapper. Every allowed or unlisted invocation is delegated with `exec /opt/pi/bin/pi` and the original argv, without PATH lookup; this prevents wrapper recursion and preserves the launcher's existing path and evidence contract. Runtime verification proves both PATH resolution and the wrapper's absolute delegation target. Explicit invocation of `/opt/pi/bin/pi` remains the prerequisite's direct-launch interface and is outside this command-name boundary.

The wrapper rejects bare/self update forms because they mutate the Pi agent and broad `--all`/`--extensions` forms because they can mutate managed extensions. For recognized install/remove/source-update forms, it rejects only a canonical npm identity found in the immutable managed-root manifest. It forwards `list`, `update --models`, recognized unmanaged npm operations, and git/URL/path installs.

A source is comparable only when canonical npm syntax occupies an explicitly recognized source slot. Scoped identity parsing removes only an optional trailing version and never percent-decodes or interprets the source as a URL. Malformed, ambiguous, aliased, reordered, or otherwise unlisted forms remain outside wrapper classification and are forwarded unchanged. The wrapper never reads, writes, suppresses, restores, or diagnoses settings or sidecar state. Classified rejections never invoke Pi and provide reviewed-root, `sync-lock`, review, and rebuild guidance; all forwarded commands preserve argv, signals, and exit status.

## Risks / Trade-offs

- [Lock synchronization can change broad closures across multiple owners] → generate and validate every candidate before a durable all-or-nothing publication transaction, then require explicit review and rebuild.
- [Resolver semantics vary with Node or npm releases] → pin the Node image by digest, assert exact Node/npm versions, and fix the complete npm argv.
- [Pinned npm may follow a redirect that Constructor cannot inspect before request] → fix the initial public registry, isolate npm configuration, reject candidates containing non-public lock URLs, and document that stronger per-request network allowlisting is outside this change.
- [Resolution could consume projected credentials or leak machine-local network configuration] → project only validated credential-free proxy/CA inputs and redact their local values; ignore rather than scan ambient npm files and environment while warning visibly that they are not applied.
- [Failure or interruption could leave a partial multi-lock commit] → use a durable journal, prior-byte backups, deterministic recovery to the complete old or new set, and keep separately owned caches outside the transaction.
- [User settings duplicate a managed root] → preserve user data, apply deterministic precedence, and diagnose the conflict.
- [A future or alternative Pi command may mutate a managed package outside the documented forms] → deliberately limit wrapper ownership to the tested documented grammar, forward all unlisted forms transparently, and update the reviewed classifier when Pi's supported command contract changes.
- [Legacy runtime state remains] → remove its launch, installer, cache, DTO, and cleanup consumers together and test that `run` is side-effect free for managed extensions.

## Migration Plan

1. Introduce root/lock validation and top-level all-or-nothing `sync-lock` without changing runtime behavior.
2. Assemble and copy the closure into an image-owned layer.
3. Add settings sidecar reconciliation and wrapper protection.
4. Remove runtime catalogs, overrides, mounts, installer, caches, DTOs, and cleanup; reject retired options with migration guidance.
5. Require rebuild for every reviewed root/lock update; rollback by restoring the reviewed TOML/lock pair and rebuilding the prior image.
